# V2.0-A Runtime Qualification

## Purpose

This document defines manual qualification tests for the committed V2.0-A lifecycle reliability implementation.

Scope:

- Render Job lifecycle and ComfyUI reconciliation
- Raw H3 output association
- Final Scene finalization and promotion
- Production Scene post-processing
- Frontend lifecycle presentation
- Selected-scene batch execution and recovery

This qualification does not cover V2.1 assembly, manifests, CSV/Resolve export, Seed Hunter, review, MCP, or storyboard work.

## Preconditions

1. Start the existing Builder GUI and the configured ComfyUI instance.
2. Confirm the Builder can load the project and display the Renders surface.
3. Create or select a project with at least three scenes in a known canonical order.
4. Prepare the selected scenes so their input and execution blockers are clear.
5. Confirm the required ComfyUI workflow nodes, models, GPU runtime, FFmpeg, and FFprobe are available.
6. Confirm the project-owned render and production directories are writable.
7. Open browser developer tools with Network and Console recording enabled.
8. Prepare a way to capture JSON responses without exposing credentials or unnecessary absolute paths.
9. Record the initial Render Job, Finalization, Production Scene, and Batch status responses.

### State fields to inspect

For Render Jobs, record:

- `state`
- `job_id`
- `scene_id`
- `comfy_prompt_id` when present
- `completion.state`
- `completion.raw_output.state`
- `completion.raw_output.failure`
- `completion.finalization_allowed`
- `finalization.state`
- `finalization.association_state`
- `finalization.retry_available`

The expected raw-output association states are:

```text
AVAILABLE
MISSING
STALE
UNSAFE
FOREIGN
AMBIGUOUS
UNKNOWN
```

For Production Scene records, inspect:

- `state`: `NOT_AVAILABLE`, `CURRENT`, `NEEDS_POSTPROCESS`, `STALE`, or `FAILED`
- post-process job `state`: `READY`, `SUBMITTING`, `SUBMITTED`, `ACTIVE`, `SUCCEEDED`, `FAILED`, or `CANCELLED`
- `output_association`
- `source_association` and `source_current` when exposed by reconciliation
- `finalization_allowed`
- `cancel.confirmed`, `cancel.confirmation_state`, `cancel.outcome`, and `cancel.evidence`

For Batch records, inspect:

- `state`, including `RUNNING`, `PAUSED_RECOVERY`, `PAUSED`, `COMPLETED`, and `COMPLETED_WITH_ISSUES`
- selected scene IDs
- each item `scene_id`, `job_id`, `disposition`, and `reason_code`
- `current_index`
- transition history and timestamps

# 1. Live ComfyUI render lifecycle

## R1. Submit an H3 Render Job and observe the queue

### Setup

- Use one prepared scene whose execution eligibility is current.
- Confirm no active Render Job exists for that scene.
- Clear any stale browser operation indicator.

### Action

1. Click **Render Scene**, or call:
   `POST /music-video-builder/projects/{project_id}/render/scenes/{scene_id}/submit`.
2. Poll:
   `GET /music-video-builder/projects/{project_id}/render/jobs`.
3. Inspect the ComfyUI queue and history while the job runs.
4. Capture the first durable `job_id` and `comfy_prompt_id`.

### Expected result

- Builder creates one durable Render Job for this attempt.
- The job progresses through submission and queue/running states without duplicate submission.
- ComfyUI shows the matching prompt ID in its queue or running list.
- The browser presents backend state and does not advance the job itself.
- The job record keeps its `scene_id` and `job_id` separate.

### Evidence to record

- Screenshot of the Renders card during queue/running state.
- `GET render/jobs` response showing the job ID and state.
- ComfyUI queue response or screenshot showing the matching prompt ID.
- Submission timestamp and first observed queue timestamp.
- Console output, if any.

## R2. Complete generation and verify raw output discovery

### Setup

- Continue R1 with the same job.
- Keep the ComfyUI output directory available for inspection.

### Action

1. Allow ComfyUI to complete the generation.
2. Poll `GET /music-video-builder/projects/{project_id}/render/jobs` until the job is terminal.
3. Inspect the job completion and raw-output projection.
4. Verify the discovered file using the project-approved output root and the recorded relative path.

### Expected result

- ComfyUI history reports technical success.
- Builder reports `completion.state=SUCCEEDED` only when the raw output association is usable.
- `completion.raw_output.state=AVAILABLE`.
- `completion.raw_output.usable=true`.
- `completion.finalization_allowed=true`.
- The output belongs to the expected prompt and production output node.
- The output is a regular readable video file under the trusted output root.
- The UI shows raw H3 output as ready or current, not merely successful because ComfyUI reported success.

### Evidence to record

- Final Render Job JSON with the completion projection.
- ComfyUI history entry for the prompt ID.
- Output filename, normalized relative path, and file size.
- Output-node and prompt-association values.
- Screenshot of the Renders card showing the discovered raw output.

## R3. Promote the raw output to Final Scene

### Setup

- Complete R2 with `completion.finalization_allowed=true`.
- Confirm the authoritative prepared scene audio exists.
- Confirm no active batch blocks manual finalization.

### Action

1. Click **Finalize Scene**, or call:
   `POST /music-video-builder/projects/{project_id}/render/jobs/{job_id}/finalize`.
2. Poll the Render Jobs endpoint and refresh the Renders surface.
3. Inspect the project-owned Final Scene metadata and media file.

### Expected result

- Finalization accepts only the validated current raw output.
- `finalization.state=FINALIZED`.
- `finalization.raw_current=true`.
- The Final Scene file is project-owned and has the expected media properties.
- The final file contains the authoritative scene audio after remux.
- The raw H3 output remains intact.
- The UI shows **Final scene: READY**.
- Finalization does not create assembly or full-song output.

### Evidence to record

- Finalization request and response status.
- Finalization metadata JSON, including output identity and fingerprint.
- Final Scene relative path and media probe output.
- Before/after hashes for raw H3 and Final Scene files.
- Screenshot showing Final Scene ready.

# 2. Render failure cases

## F1. ComfyUI success with a missing output

### Setup

Use a disposable scene and one of these controlled conditions:

- Run a successful ComfyUI history entry that produces no Builder-owned output; or
- Remove the expected output before Builder performs output discovery.

Do not alter source code. Restore the disposable project after the test.

### Action

1. Reconcile the Render Job through `GET render/jobs`.
2. Attempt Final Scene finalization.
3. Refresh the Renders surface.

### Expected result

- The technical Render Job may remain `SUCCEEDED`.
- `completion.state=SUCCEEDED_OUTPUT_UNAVAILABLE`.
- `completion.raw_output.state=MISSING` or `UNKNOWN`, depending on the observed evidence.
- `completion.finalization_allowed=false`.
- Finalization returns a structured failure containing job ID, scene ID, association state, failure reason, and retry availability.
- The UI does not show raw output as ready and does not offer an enabled Finalize action.
- No Final Scene promotion occurs.

### Evidence to record

- ComfyUI history response.
- Render Job completion projection.
- Finalization HTTP status and JSON error body.
- Screenshot of the missing-output message and disabled action.
- Confirmation that no new Final Scene output was written.

## F2. Previously discovered output becomes stale

### Setup

- Complete R2 so the association is `AVAILABLE`.
- Keep a copy of the valid output identity.

### Action

1. Delete the discovered raw output, or replace it with different bytes while keeping the same path.
2. Poll `GET render/jobs`.
3. Attempt finalization.
4. Refresh the UI.

### Expected result

- Builder detects that the physical artifact no longer matches the durable association.
- `completion.raw_output.state=STALE`.
- `completion.finalization_allowed=false`.
- Finalization reports the stale association without collapsing it into a generic successful state.
- A prior valid Final Scene remains intact.
- The UI displays a stale or unavailable raw output and blocks Finalize.

### Evidence to record

- Original and replacement/deletion timestamps.
- Original and current file identities or hashes.
- Reconciled Render Job JSON.
- Finalization error response.
- Screenshot showing stale state and preserved prior Final Scene.

## F3. Unsafe or foreign output path

### Setup

Use a disposable job record or controlled ComfyUI output fixture. Test each condition separately:

- parent traversal such as `../outside.mp4`;
- symlinked output path;
- output outside the trusted ComfyUI output root;
- output associated with a foreign prompt or output node.

Back up the disposable record before injecting the condition.

### Action

1. Reconcile the job.
2. Inspect the completion projection.
3. Attempt Final Scene finalization.
4. Restore the disposable fixture.

### Expected result

- Traversal or symlink escape reports `UNSAFE`.
- Foreign prompt or node association reports `FOREIGN`.
- No unsafe or foreign file enters Final Scene.
- Finalization remains blocked.
- The structured error preserves the association state and includes the failure reason.
- The UI does not expose the unsafe absolute path as a usable output.

### Evidence to record

- Sanitized association fields and relative path.
- Output-root and symlink test setup.
- Completion and finalization JSON.
- HTTP status and structured error body.
- Screenshot showing the blocked action.

## F4. Cancel a Render Job

### Setup

- Submit a scene and wait until the Render Job is pending or running.
- Keep the ComfyUI queue visible.

### Action

1. Click **Cancel**, or call the Render Job cancellation route.
2. Observe the ComfyUI queue and running state.
3. Poll Builder status until the cancellation outcome stabilizes.

### Expected result

- Pending jobs use queued deletion.
- Running jobs use the targeted running interruption operation.
- Builder records the cancellation request and observed terminal outcome.
- A cancelled or interrupted job cannot finalize without a usable output.
- A cancellation does not delete a prior valid Final Scene.
- If ComfyUI cannot confirm the outcome, Builder keeps the job available for reconciliation rather than claiming a usable success.

### Evidence to record

- Cancellation request timestamp.
- ComfyUI queue before and after cancellation.
- Render Job transitions and final state.
- Cancellation error or acknowledgment response.
- Screenshot of the cancellation state.

## F5. Interrupt the ComfyUI process during a render

### Setup

- Submit a Render Job and wait until it is queued or running.
- Record the job ID, prompt ID, and current Builder state.
- Coordinate the restart so no unrelated ComfyUI work is affected.

### Action

1. Stop or terminate the ComfyUI process during execution.
2. Refresh Builder status while ComfyUI is unavailable.
3. Restart ComfyUI.
4. Poll Builder again and allow bounded reconciliation to complete.

### Expected result

- Builder does not invent a successful completion from missing telemetry.
- The job enters an observable reconciliation, unknown, interrupted, cancelled, or orphaned outcome based on durable queue/history evidence.
- A missing output never becomes finalization-ready.
- After ComfyUI restarts, Builder reconciles the existing prompt instead of submitting an unintended duplicate.
- The UI communicates recovery or required attention.

### Evidence to record

- ComfyUI stop/start timestamps.
- Job and prompt IDs.
- Status responses before, during, and after restart.
- Transition history showing reconciliation.
- Screenshot of the recovery state.

# 3. Production Scene qualification

## P1. Successful postprocess and Production Scene promotion

### Setup

- Complete and finalize a current Final Scene.
- Select a qualified production method such as `rtx_vsr_fast`.
- Confirm the selected method's nodes, models, and hardware are available.

### Action

1. Start postprocess from the scene surface, or call:
   `POST /music-video-builder/projects/{project_id}/scenes/{scene_id}/render/postprocess/start`.
2. Observe ComfyUI queue/history and the scene postprocess status route.
3. Reconcile the successful postprocess job.
4. Finalize/promote the Production Scene through the existing scene action.
5. Refresh Production status.

### Expected result

- The postprocess job progresses through `SUBMITTED` or `ACTIVE` to `SUCCEEDED`.
- Output discovery identifies the owned postprocess file.
- `output_association.state=AVAILABLE` and `usable=true`.
- The Final Scene remains the source authority and remains unchanged.
- Production Scene promotion validates dimensions, timing, frame count, codecs, audio, path ownership, and identity.
- Production status becomes `CURRENT`.
- The UI shows Production Scene ready.

### Evidence to record

- Postprocess job JSON and ComfyUI history response.
- Output association and source-currentness projections.
- Production metadata and output identity.
- Media probe results.
- Screenshots of postprocess progress and Production Scene ready state.

## P2. Failed postprocess

### Setup

Use a disposable Final Scene and cause one controlled failure:

- ComfyUI execution failure;
- unavailable production method;
- invalid output media;
- missing or unreadable postprocess artifact.

### Action

1. Start postprocess.
2. Allow the controlled failure to reach Builder reconciliation.
3. Poll the scene postprocess status and Production status.
4. Inspect available retry actions.

### Expected result

- The postprocess job becomes `FAILED` with a durable failure code and message.
- Production status becomes `FAILED`, `NEEDS_POSTPROCESS`, or another explicit non-current state, not `CURRENT`.
- Raw H3 and Final Scene remain intact.
- A retry is available only when the recorded failure permits retry.
- The UI shows the failure and an actionable retry or recovery message.

### Evidence to record

- Failure injection details.
- Postprocess transitions and failure document.
- Production status response.
- Final Scene and Raw H3 identities before and after.
- Screenshot of the failure state.

## P3. Cancel postprocess and distinguish confirmation

### Setup

- Start a postprocess job and wait until it is pending or running.
- Prepare a second disposable run where the prompt is absent from the queue.

### Action

1. Cancel the pending or running job.
2. Record the ComfyUI operation and returned result.
3. In the second run, cancel after the prompt disappears from queue/history, or after history reports a terminal result.
4. Poll the scene status after each case.

### Expected result

For an acknowledged queue deletion or running interruption:

- The job becomes `POSTPROCESS_CANCELLED`.
- `cancel.confirmed=true`.
- `cancel.confirmation_state=CONFIRMED`.
- The evidence identifies the acknowledged operation.

For an absent prompt or terminal history result:

- Builder does not overwrite a known ComfyUI terminal outcome with a false cancellation.
- The record remains available for reconciliation when cancellation is unconfirmed.
- `cancel.confirmed=false`.
- `cancel.confirmation_state` and `cancel.outcome` identify the unconfirmed or history-terminal case.
- Final Scene and any prior Production Scene remain intact.

### Evidence to record

- Queue state before cancellation.
- ComfyUI delete or interrupt request and response.
- `cancel` object from each returned record.
- Durable transition history.
- Screenshots for confirmed and unconfirmed cases.

## P4. Delete Production output after success

### Setup

- Complete P1 through a successful postprocess job.
- Record the postprocess output identity and Production Scene status.

### Action

1. Delete the promoted Production Scene output after success, or modify it so its identity no longer matches.
2. Refresh the scene Production status.
3. Reconcile the terminal postprocess job.
4. Attempt to use the Production Scene as current.

### Expected result

- Terminal `SUCCEEDED` does not bypass artifact validation.
- The terminal job exposes an unavailable or stale output association.
- Production status is no longer `CURRENT`.
- Promotion or downstream use is blocked until a valid output exists.
- Final Scene and Raw H3 remain intact.

### Evidence to record

- Pre-deletion production identity.
- Deletion or replacement timestamp.
- Post-reconciliation job projection.
- Production status response.
- Screenshot showing the stale or unavailable Production Scene.

# 4. Frontend verification

## U1. Refresh during render

### Setup

- Start an H3 Render Job and wait until it is queued or running.
- Confirm the Renders card shows active lifecycle state.

### Action

1. Reload the Builder page during the render.
2. Wait for the initial render job request and subsequent polling.
3. Compare the displayed job ID and state with the backend response.

### Expected result

- The browser reconstructs the card from durable backend state.
- The active state reappears without duplicate submission.
- Polling resumes and stops only after the backend reports a truthful terminal/readiness state.
- The UI does not rely on volatile browser memory to claim progress or completion.

### Evidence to record

- Screenshot before reload and after reload.
- Network requests after reload.
- Matching job ID and state in the response and UI.
- Console errors, if any.

## U2. Refresh after completion and Final Scene promotion

### Setup

- Complete one Render Job and, separately, complete Final Scene finalization.

### Action

1. Reload after ComfyUI generation completes but before Final Scene finalization.
2. Verify the raw-output and Final Scene labels.
3. Finalize the scene.
4. Reload again after finalization.

### Expected result

- After generation only, the UI distinguishes raw H3 readiness from Final Scene readiness.
- After finalization, the UI shows Final Scene ready only when the completion and finalization projections permit it.
- The UI remains truthful after reload and does not derive readiness from a raw output field alone.

### Evidence to record

- Screenshots at both reload points.
- Render Job JSON showing `completion` and `finalization` projections.
- Visible labels and enabled/disabled actions.

## U3. Display stale state

### Setup

- Start from a valid raw output or Production output.
- Remove or modify the artifact using a disposable project.

### Action

1. Refresh the Builder.
2. Wait for HTTP reconciliation.
3. Inspect the scene card and available actions.

### Expected result

- The card shows `STALE`, `MISSING`, or another specific association failure rather than `READY`.
- Finalize or Production promotion remains disabled when the projection blocks it.
- The UI retains historical context without calling the artifact current.
- The stale message identifies the recovery action without exposing unsafe filesystem details.

### Evidence to record

- Screenshot of the stale card.
- Corresponding completion/finalization/production JSON.
- Action button states.

## U4. Display error and retry information

### Setup

- Create a controlled failed Render Job, finalization failure, or postprocess failure.
- Keep browser Network and Console recording enabled.

### Action

1. Refresh the Builder.
2. Open the relevant error state.
3. Inspect the request response and the rendered error message.
4. Attempt the offered retry only when the projection says retry is available.

### Expected result

- The UI displays a sanitized failure message.
- The HTTP response exposes the relevant job ID, scene ID, association state, failure reason, and retry availability for finalization errors.
- The UI does not display raw prompt IDs or unnecessary absolute paths in normal user copy.
- A disabled retry remains disabled when `retry_available=false`.
- A valid retry creates a new attempt or postprocess job without overwriting history.

### Evidence to record

- HTTP status and sanitized response body.
- Screenshot of the error card.
- Retry button state.
- Old and new job IDs when a retry runs.

# 5. Batch verification

## B1. Run selected scenes only

### Setup

- Use a project with at least three prepared scenes in canonical order.
- Select two non-adjacent scenes, for example scenes 1 and 3.
- Confirm no active batch exists.

### Action

1. Preview the selection with:
   `POST /music-video-builder/projects/{project_id}/render/batch/preview`
   and body:
   ```json
   {"scene_ids": ["<scene-1-id>", "<scene-3-id>"]}
   ```
2. Start the same selection with:
   `POST /music-video-builder/projects/{project_id}/render/batch/start`.
3. Poll:
   `GET /music-video-builder/projects/{project_id}/render/batch`.
4. Observe Render Jobs and ComfyUI queue activity for all scenes.

### Expected result

- The preview and start use the same selected plan.
- The batch mode is selected, not all-ready mode.
- Only the requested scene IDs receive batch items and new work.
- The batch follows project scene-list order, not filename or prompt-ID order.
- Each item retains its own `scene_id` and `job_id`.
- Unselected scenes remain unchanged.

### Evidence to record

- Preview request body and response.
- Start request body and response.
- Batch record with selected scene IDs and item list.
- Render Job list before and after start.
- ComfyUI queue observations.
- Final batch item dispositions and timestamps.

## B2. Reject a malformed batch request

### Setup

- Use a valid project with no active batch.
- Prepare a request tool or browser Network override that can send malformed JSON with a non-empty body.

### Action

Send malformed or invalid selection bodies to batch preview or start, including:

```text
{"scene_ids":
{"scene_ids": []}
{"scene_ids": ["not-owned"]}
{"unexpected": true}
```

Also send a non-empty body that is not valid JSON.

### Expected result

- The route returns HTTP `400`.
- The response explains the invalid body or selection.
- The malformed body never becomes an empty selection.
- The server does not start a batch.
- An absent or genuinely empty body retains the documented all-ready semantics where that route supports it.

### Evidence to record

- Exact request body and headers, including `Content-Length` where relevant.
- HTTP status and response JSON.
- Batch status before and after, showing no new active batch.
- Server log entry, if available.

## B3. Recover an interrupted batch

### Setup

- Start a selected-scene batch with at least two items.
- Wait until the batch is executing and one item is active.
- Record the active batch ID, current index, scene ID, and Render Job ID.

### Action

1. Stop the Builder backend or terminate the runner process while the batch remains active.
2. Restart the existing Builder backend and GUI.
3. Request:
   `GET /music-video-builder/projects/{project_id}/render/batch`.
4. Inspect the active batch and related Render Job/Postprocess records.
5. Resume the batch using:
   `POST /music-video-builder/projects/{project_id}/render/batch/resume`.
6. Continue polling until the batch completes or pauses with an explicit issue.

### Expected result

- Startup/status reconciliation detects the durable active batch.
- The batch enters `PAUSED_RECOVERY` or another explicit recovery state when attention is required.
- The system does not leave a durable `RUNNING` batch without a live runner.
- The runner reconciles the active Render Job or postprocess job before deciding whether to continue.
- Recovery does not duplicate a completed scene or overwrite prior job history.
- Resume continues from the correct item and respects the original selected set.
- The bounded transition budget prevents unbounded recursive progression.

### Evidence to record

- Batch and item JSON before interruption.
- Backend stop/start timestamps.
- First status response after restart.
- Recovery state and transition history.
- Render Job/Postprocess reconciliation responses.
- Resume response and final batch record.
- Evidence that no duplicate job was submitted for the completed item.
